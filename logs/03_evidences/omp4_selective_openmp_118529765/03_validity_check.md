# 03 有效性核查 — [O34] 四对象选择性 OpenMP

目的：独立复核 02 的结论，列出反证、未验证假设与适用边界；给出合规判定与
本分支的处置意见。

## 1. 合规性

| 规则维度 | 判定 | 依据 |
|---|---|---|
| 浮点运算次序不变 | ✅ | 只加 `!$OMP PARALLEL DO`，未改表达式、未加 reduction、未改循环次序；四次运行时间步轨迹 sha256 完全一致（`fa498694…e44b0`） |
| 不改算例参数 | ✅ | harness 对 `NTIMES/NtileI/NtileJ/DT/NDTFAST` 做正则断言 |
| 不改验证脚本 | ✅ | `vali.py` sha256 门禁 |
| 允许的并行化手段 | ✅ | OpenMP 是官方明确允许项；未触碰 I/O、未改 MPI 语义 |
| 二进制/源码可追溯 | ✅ | 4 个 .F + makefile + 两个二进制均按 sha256 门禁进入作业 |

**结论：本改动完全合规。它被否决的唯一原因是没有性能收益。**

## 2. 对 02 各条结论的复核

### 2.1 "四个区间的 s = 1.74–1.95" — 成立，但有一处需限定

推导依赖三个前提，逐条核查：

1. **`cpu_time()` 是跨线程累加** —— Stage 88 已用既有 5 个 OpenMP 对象独立
   标定过（总 CPU/墙钟 = 1.3057，与 s = 1.651 自洽）。本次 A2 的 1.2727
   与之同量级，前提成立。
2. **并行区内两线程都满载** —— `KMP_BLOCKTIME=0`，空闲线程休眠不计 CPU。
   若线程间负载不均，实际 CPU_B < 2 × 墙钟_B，则真实 s 会**低于**推导值。
   因此 1.857 是 s 的**上界**估计。
3. **区间内被并行的部分接近 100%** —— 对 `rho_eos`、`hmixing` 成立（单一
   主循环）。对 `rhs3d`、`step3d_uv` 只并行了各 2 个循环，区间内仍有串行残余，
   所以这两者的"区间级 s"低估了被并行循环本身的加速比。

综合：s 的合理区间是 **1.6–1.9**，取 1.857 作点估计不影响任何结论
（即使 s = 1.5，应省墙钟仍有 3.28 s/rank = 2.6%，仍然全部丢失）。

### 2.2 "省下的时间变成了等待" — 成立，且有独立支撑

三条互相独立的证据：

- **记账闭合**（02 §4）：H1 预测 +1.09 s/rank，实测 +0.555 s/rank；
  H2 预测 +5.63 s/rank，偏差 5 s。H2 被定量排除。
- **增长的选择性**：增长只出现在含 MPI 的区间（GLS、3 类 halo、Omega、
  coupling），纯计算区间（step2d −0.7%、t3dmix4_s −0.1%、biology +0.5%、
  压力梯度 −0.4%）完全不动。若是系统性变慢（如内存带宽争用、频率下降），
  纯计算区间也该变慢。它们没有。
- **可重复性**：GLS 的 +20.8% 在 B1/B2 两次运行中重现（1178.3 / 1171.0，
  差 0.6%），A1/A2 中同样稳定（983.5 / 974.7）。信号是噪声的 20 倍以上。

### 2.3 反例检查：有没有可能是 OpenMP 本身的开销？

fork/join 次数：新增 6 个并行区 × (144 + 720) 步 × 每步调用次数 ≈ 10⁴ 量级。
即使按 100 µs/次的悲观开销，也只有 ~1 s/rank，且这部分开销会记在**目标区间
自己**的计时器里，而不是 GLS/halo。观察到的 +412 CPU-s 出现在未改动区间，
与 fork/join 开销的位置不符。排除。

### 2.4 反例检查：会不会是节点内存带宽争用？

B 中四个区间由每节点 16 线程变为 32 线程，带宽需求翻倍。若带宽饱和，
这四个区间的 s 应显著低于 2（观察到 1.74–1.95，说明没饱和），
且**同一节点上的其它区间不受影响**（它们与这四个区间在时间上不重叠）。
纯计算区间 CPU 无变化，与"无带宽争用"一致。排除为主因。

### 2.5 未能验证的部分：关键路径上的偏斜到底来自哪里

02 §6 判定"关键路径由 rank 到达偏斜决定"，这是从"计算变快但墙钟不变"
反推出来的**必然结论**，但**偏斜的来源本次没有测量**。候选：

- rank 0 的 NetCDF 读 + `mp_bcast` 串行路径（B2 的 `Processing of input data`
  Grid 02 从 110.4 涨到 152.5，量级 +42 CPU-s，方向吻合，但该计时器
  运行间噪声本身就大，不足以定论）
- 嵌套网格（Grid 01/02）耦合点上的 `mp_assemble` / point data gathering
- 节点/核心级抖动（OS jitter、频率）
- 8×8 分块下各 rank 的 halo 体积差异

**要区分这些，需要一次带 per-rank 到达时间戳的探针作业，本次未做。**
在做这个测量之前，任何"减少同步开销"的候选都缺乏靶向依据。

### 2.6 A1 冷启动结论的强度

"95% 的 A1−A2 差距由 Reading of input + broadcast 解释"是单点观测
（只有一组 A1/A2）。B1−B2 的墙钟差只有 0.018 s，说明第二次之后已经热态，
方向一致但样本量为 1。作为**方法学告警**足够，作为定量修正系数不够。

## 3. 结论的适用边界

本次结果**只否证**了"给更多 3-D 计算对象加线程并行"这一类做法，
在以下条件下成立：

- 64 rank × 2 线程、8×8 分块、4 节点独占、本平台与本工具链
- 目标是**已经不在关键路径上**的 3-D 计算区间

它**没有**否证：

- `step2d`（2D kernel，A2 占 1335.6 CPU-s = 13.2% 的 CPU）。step2d 与 halo
  交换交织，性质与这四个对象不同，本次实验不构成对它的判决。但 02 §3 显示
  step2d 的 CPU 在 B 中反而降了 0.7%，说明它同样没有被"释放的时间"喂饱，
  仍需独立验证。
- 改变 rank/线程配比、分块形状（NtileI×NtileJ 的长宽比会改变 halo 体积）
- 减少同步点数量或重叠通信与计算
- 非计算路径（rank 0 I/O、广播、散射）

## 4. 对既有方法论的修正（重要）

1. **"区间占比 × 加速比"的收益外推模型对 3-D 计算区间已失效。**
   Stage 89 预测 1.5–2.5% 墙钟收益，计算部分预测得相当准（实测应省 3.65%），
   但整机收益是 0。今后任何此类估算必须先证明目标区间在关键路径上。
2. **CPU 时间的"增加"不等于"变慢"。** 忙轮询的 MPI 等待与真实计算在
   `cpu_time()` 里无法区分。需要区分时，必须看该区间是否含 MPI 调用。
3. **rank 间 CPU 离散度不能用作负载均衡指标**（忙轮询让等待方也满载）。
4. **A-B-B-A 的第一次运行是冷启动离群点。** 后续 harness 应增加一次丢弃的
   预热运行，或继续以 `both_B_faster` 而非 `gain_percent` 作为主门禁 ——
   本次正是 `both_B_faster=False` 拦住了 `gain_percent=1.12%` 的假阳性。
5. **harness 的 profile 过滤正则有误**：写的是 `Corrector 3D momentum`，
   日志实际为 `Corrector time-step for 3D momentum`，导致本次四个目标之一
   未进入 `profile_extract.txt`，只能回到 `model.log` 补取。需修正。

## 5. 处置建议

- **[O34] 分支：否决，不并入。** 判据：`verdict=STOP_BRANCH`，
  热态对比 B 比 A 慢 0.45%，`both_B_faster=False`。
- 保留 4 个 .F 的改动与 makefile 4 行（已按 sha256 记录在 01 中），
  以便未来若同步瓶颈被解决可以立即复用 —— 它们本身是正确且合规的。
- 这是继 Stage 85（allgatherv）之后**连续第二次 STOP_BRANCH**，
  按 plan.md 既定规则触发强制调研循环。
- 下一步的前置条件：**先测量 rank 到达偏斜**，再决定优化方向。
  在没有这个测量之前继续猜测同步开销的来源，重复本次"方向正确、
  靶点错误"的风险很高。
