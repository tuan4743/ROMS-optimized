## 0. 全局数据布局（一切性能讨论的出发点）

```fortran
! mod_ocean.F allocate_ocean
t    (LBi:UBi, LBj:UBj, N, 3, NT)   ! 5 维：i, j, 34 层, 3 时层, 17 示踪量
u, v (LBi:UBi, LBj:UBj, N, 2)       ! 4 维：i, j, 34 层, 2 时层
ru,rv(LBi:UBi, LBj:UBj, 0:N, 2)     ! 0:N 表示 W 面
W, wvel (LBi:UBi, LBj:UBj, 0:N)
zeta/ubar/vbar (LBi:UBi, LBj:UBj, 3)  ! 2D 三时层
```

- Fortran 列主序：**i 连续**，stride = 1；j 步长 = tile 宽（≈45）；k 步长 ≈ tile 面积（≈2000）；
  时层步长 ≈ 34×面积；tracer 步长 ≈ 3×34×面积。**跨 tracer 访问 = 跳 200K 字节级的大步长**。
- 8×8 tile 剖分，粗网格每 tile ≈ 45×41 内点（+2~4 ghost），细网格 ≈ 30×31。t 数组每 rank ≈ 30 MB（两网格合计更大）→ **远超 L3（每节点 Hygon 7185 L3 ≈ 128 MB 总量，32 核共享）**，任何"全数组缓存复用"都不可能。
- 结论：内核以**内存带宽为天花板**；每遍扫描 i×j×k×tracer 越少越好（这就是为什么"减少重复扫描"能生效）；i 内层必须连续（编译器向量化前提）。

## 1. step2d（2D 快模，step2d_LF_AM3.h，2486 行）

### 数据结构与内存
- 输入：zeta(:,:,krhs/kstp/knew)、ubar/vbar(:,:,3)、rubar/rvbar/rzeta(:,:,2)、DUon/DVom/DU_avg1/2、Zt_avg1（2D，全在 cache 内）。
- 局部：UFx/UFe/VFx/VFe/grad/Dgrad/Drhs/gzeta/gzeta2/zwrk 等 2D 栈数组（每 tile ≈ 45×45×8B ≈ 16 KB，多块几十 KB，**完全驻留 L1/L2**）。
- 无 3D 数组 → 本内核是"L1 密度型"，不是带宽型。

### 循环结构与实际运算
- 顺序：krhs 时间层的通量组装（DUon）→ 滤波累加（weight 表）→ ζ 推进（LF/AM3）→ 2D 动量 RHS 五段（压力梯度/平流/科氏/曲率/黏性）→ 动量积分（深度加权）→ 湿干 → 边界 → 滤波收尾。
- 每快模步对 i×j（≈1800 点）做 ~10 遍独立扫描，每点 ~30-60 次浮点；**全部是 i 内层连续访问**。
- 压力梯度段每点含 2 次乘法除法少的运算，但 gzeta² 等要重复算 3 次（gzeta/gzeta2/gzetaSA 三个数组都存中间量）→ 这是"算 3 遍还是存 3 个数组"的经典权衡，此处选后者。

### 线程/MPI 行为
- 被调用 `(nfast+1)` 次预测 + `nfast` 次校正/3D 步（nfast=42 → **85 次调用**，最后一次仅滤波收尾）：**单 3D 步内 85 次调用**，每次调用都伴随一次 `!$OMP BARRIER` 和 2-4 次 `mp_exchange2d`（每次 1-3 个变量，EW/NS 两对，每消息 ≈ 2×45×8B ≈ 720 B）→ **快模段是"小消息高频交换+全线程屏障"的节奏**，等待开销占比高。
- 单线程段：wetdry、set_DUV_bc、obc_flux。
- 实测：G02 阶段计时 step2d 16.4 s/122 s 采样（13%）；MPI 内 2D halo 占 4.8%（全部消息中最大单项之一）。

### 编译器行为
- 压力梯度/平流段是规整三重循环，ifort 可自动向量化（AVX2 下 4 double/条）；但 `IF (PREDICTOR_2D_STEP)` 分支把三段挤在同一循环位置 → 分支外提决定向量化成败。
- 本内核无 pow/exp/除法热点（除 Drhs 求逆一次），FMA 关闭后（-no-fma）乘加对数量翻倍，仍是 2D 数组量级，可忽略。

### 优化历史（程序员结论）
- 改循环/合并段：无收益（编译器已覆盖）；`t3dmix` 压栈类技巧在这里无意义（数组本来就小）。
- 湿干逻辑每次快模步重算掩膜 → 曾尝试缓存（Step2d 相关），实测无差：掩膜段是 O(点) 一次扫描，非热点。
- **结论：快模耗时不在计算，在 84 次调用/3D 步的同步与通信节奏**。→ 这就是"减少 2D halo 交换次数（合并变量）"是唯一有理论空间的优化，实测稀疏合并无益（消息太小）。

## 2. rhs3d（3D 动量 RHS，1670 行）

### 数据结构与内存
- 输入：u/v(:,:,:,nrhs)、Hz、Huon/Hvom、Akv、den、prsgrd 输出；输出 ru/rv(:,:,:,nrhs)（m⁴/s²）。
- 局部：UFx/UFe/VFx/VFe/grad/Dgrad/FC/CF/DC 等 (Imin:Imax)×(0:N) 列数组——**k 维度只存一列**（i×k 面板），符合"逐 j 处理、k 列驻寄存器/L1"的 ROMS 惯例。

### 循环结构与实际运算
- **K_LOOP 在外（k=1..N）、j 内、i 最内**：每 (j,k) 一个 i 扫描。u/v 数组按 i 连续 → 每个 (j,k) 面板访问 u(i,j,k,:) 连续 ~45 个 double，**每列 8B×45×3 数组 = 1 KB，完美 L1**。
- 各段运算量（每点，粗估）：
  - 体力风/底应力：仅顶层/底层（k 判分支）；
  - 科氏：每点 ~6 flops；
  - 曲率：~10 flops（dndx/dmde 查表）；
  - 水平黏性（visc4 双谐波）：每点 ~40 flops（4 阶模板读 5×5 邻域 → **内存访问是计算量的 2-3 倍**，这是带宽受限段）；
  - 水平平流（4 阶）：每点 ~30 flops，读 3×3 邻域；
  - 垂向平流（UV_SADVECTION 样条）：先对整列做 3 对角求解（FC/CF 递推，每列 ~34×3 次运算），再半拉格朗日通量（每列 ~34×若干次比较/乘加）——**串行依赖链在 k 方向，无法向量化，只能 j/i 并行**。
- 总浮点/点 ≈ 100-150 flops × 1800 点 × 34 层 ≈ 8-9 Mflops/tile/次调用。

### 线程/MPI 行为
- 纯 tile 内计算，无通信；OpenMP 按 tile 并行。j 内层循环不可 OMP（依赖 FC 列递推，但那是 k 方向；j 与 j+1 独立）→ 理论上可 j 并行，实测并入 tile 并行足够。
- 实测：阶段计时 rhs3d 26.8 s/122 s（22%），但 O33 全量 PROFILE 中 3D rhs 仅 1.3%——**差异来自计入 pre_step3d 与否的口径**（队友 s22b 把 RHS 计入 pre_step3d 同段）。按 VTune：rhs3d 本体不是热点，热点是它的"邻居"。

## 3. pre_step3d（示踪量+动量预测器，1145 行）— 单函数第一热点

### 数据结构与内存
- 输入：t(:,:,:,nstp,:)（17 个 tracer 全量）、Huon/Hvom、W、Akt；输出 t(:,:,:,3,:)。
- 局部：FX/FE（水平通量，每 (j,k) 面板）、FC/CF/DC/BC（垂向列）、swdk、grad/curv。

### 循环结构（关键：**先 k 后 j，还是先 j 后 k？**）
- 水平平流：`T_LOOP1 (itrc) → K_LOOP (k) → J → I`：**对每个 tracer 逐层扫**。
- 垂向扩散：`J → itrc → K → I`：逐列三对角。
- **两个不同的循环嵌套顺序并存** → t 数组被以两种顺序扫描（k 外层扫面板 vs j 外层扫列），cache 行为不统一，但每段都是 i 连续 → 向量化不受影响。
- 每 tracer 每层：水平平流 ~25 flops + 4 阶修正；垂向人工连续性每列一次；垂向平流样条每列 ~34×10 flops；垂向扩散三对角每列 34×6 flops（前后代）。
- 17 tracer × 34 层 × 1800 点 ≈ **1.04M 点·tracer·层**，每点 ~50-80 flops → 每次调用 ~60-80 Mflops，且**读 t(nstp,:) 写 t(3,:)，两次全量 17×34×1800×8B ≈ 8.3 MB/tile**，L2 边缘（每核 L2 512 KB-1 MB）→ 带宽主导。

### 向量化
- 水平平流 4 阶中心：i 方向 5 点模板，可向量化（gather 平移 1-2 的读 → AVX2 下编译器一般能处理）；掩膜乘法打断（umask 数组查找）。
- 垂向样条/三对角：k 方向串行依赖，**不能向量化**；只能靠 i 方向多列并行（编译器自动矢量化 i 循环内的独立列 → 需要 FC/CF 数组按 (i,k) 布局，本代码正是）。
- MPDATA 路径：pre_step3d 是上游一阶（无向量化问题），反扩散在 step3d_t。

### 优化历史
- 队友 S26/S27 fast=2 尝试（step3d_t+pre_step3d 快速数学）：**vali 失败**（Dongsha u=0.000071 超限）→ 本文件是精度敏感区，fast 数学不可碰。
- Stage 90 四对象 OMP（step3d_t/pre_step3d/gls/biology 各加 OMP）：实测无收益（机制：tile 已满线程，函数内再开线程无空闲核）→ 否决。**但队友 rho_eos 整例程 OMP 不同**：rho_eos 是纯计算，PRIVATE 数组小，主线程被 tile 循环占满后 j 循环并行把同一 tile 内的工作分摊给 2 线程 → 收益来自"把 1 线程的 tile 计算切成 2 线程"。

## 4. step3d_uv（3D 动量校正器，1478 行）

### 结构
- 每 j：AM3 时间推进（u(nnew) += 0.25·dt·面积·ru）→ 垂向黏性隐式（FC/CF/BC/DC 列三对角，LU+前代+回代）→ 边界 → **2D/3D 耦合段**。
- 耦合段（1186-1207，程序员视角的经典片段）：
  ```
  do k=N,1,-1 : Huon(i,j,k)=0.5*(Huon+u*DC(k)); FC(0)+=Huon(i,j,k)   ! 垂向积分 3D 通量
  FC(0)=DC(0)*(FC(0)-DU_avg2(i,j))                                    ! 减快模滤波平均通量
  do k=1,N   : Huon(i,j,k)-=DC(k)*FC(0)                               ! 每层减同量偏差
  ```
  → 3D 通量的垂向平均被强制等于快模时间平均通量（barotropic correction）。**每 j 一个 k 方向归约 + 广播，串行依赖在 k，但 j 独立**。
- 运算量：~34×6 flops/列 × 1800 列 ≈ 0.4 Mflops/次调用——**全内核最轻**（实测阶段占比 2.5%，VTune 中几乎不可见）。
- 教训记录：本文件原始版本有"每 j 重新读 Akv 列"，SPLINES_VVISC 下 Akv 被当 W 面插值（0.5·(Akv(k-1)+Akv(k))）——无优化空间，编译器已内联。

## 5. step3d_t（示踪量校正器，1300 行）

### 结构（每 tracer、每 j）
1. 水平平流通量（与 pre_step3d 同族）；MPDATA 模式含反扩散（本工程预处理器选型：TS_MPDATA 时在 step3d_t 内做 anti-diffusive 修正，见 893-1000）。
2. 垂向平流通量（显式，W 面值）。
3. 垂向扩散隐式三对角（1067-1136）：
   - 系数 `FC(i,k) = −dt·λ·Akt(i,j,k,ltrc)/(z_r(k+1)−z_r(k))`；
   - **S38 优化点**：ltrc = MIN(NAT,itrc) → itrc≥3 的 14 个生态 tracer 复用同一套 Akt 系数，**免掉 14 次 FC/BC 重算**（原代码 itrc=1..15 各自重算，实际 Akt 只有 2 个独立值）。实测 −0.67%（1day）。
   - 三对角按 (i,k) 面板做：前代 k=2..N-1、回代 k=N..1——**i 内层向量化 + k 串行依赖**。
4. 惰性示踪量年龄、t3dbc 边界、nudging、rmask。
5. **mp_exchange4d 整块交换 t(:,:,:,nnew,:)**：17 tracer 一次打包，消息 ≈ 17×34×45×8B ≈ 208 KB/方向 → **最大单消息**（4D halo 占 MPI 时间 7.1%）。

### 运算与带宽
- 每 tracer：水平平流 ~25 flops/点 + 垂向 ~40 flops/点 + 扩散 ~15 flops/点 ≈ 80 flops/点 × 1M 点 ≈ 80 Mflops/次调用；带宽 ~16 MB/tile。
- 时间层写回：t(nnew) 与 t(3) 各一次全量写 → 与 pre_step3d 合计**每 3D 步 t 数组被全量读+写至少 4 遍**（预测量 nstp→3、校正量 3→nnew、生态回写 nnew、4D 交换打包）→ 这就是"17 示踪量计算是带宽瓶颈"的直接证据。

### 优化历史
- Step3d_t 延迟交换（O33 系列 omphot）：把 4D halo 从校正器开头挪到结尾 → 少量收益（O33 累积）。
- S38 vdiff 系数复用：采纳（−0.67%）。
- S26 fast=2：vali 超限，关闭。
- **可答问**：为什么不能把 17 tracer 合并成 1 个循环？（需要 17 个独立三对角，循环融合后 i 方向向量化宽度不变，但每次迭代读 17 列 → 数据量不变，只是减少外层循环开销——ifort -ipo 已做类似融合，实测无差。）

## 6. rho_eos + prsgrd（状态方程 + 压力梯度）

### rho_eos（885 行）
- 结构：`j → k → i` 三重循环，每点独立（**无列依赖、无归约**——理想并行形态）。
- 每点运算：C(0..2) 三个 Horner 多项式（~15 mul/add）+ den1 组合（~10）+ bulk 的 7 个多项式（~30）+ 原位密度 1 除法 + 1 倒数 → **~60 flops/点，其中 1 次除法、0 次 exp**。
- 17×34×1800 点 → 每调用 ~60 Mflops，纯计算无通信。
- **向量化**：Horner 链有依赖（C(0)=T*(T*(T*(T*(T*q+...))))），但不同 i 点独立 → i 内层向量化 = 4 路并行 Horner（AVX2），编译器可做；除法序列化为倒数+乘法（ifort 默认）。
- **S42 优化**：整例程 `!$OMP PARALLEL DO` 沿 j 切分（PRIVATE C/bulk 等小数组）——机制见第 3 节末。**热对热收益实测：S42 整体 −1.44%（含 S38）**。
- 答辩点：为什么这个例程值得 OMP 而 step3d_t 不值得？（rho_eos：单循环、无跨层依赖、无 halo、PRIVATE 变量小 → 线程开销可摊销；step3d_t：有 k 方向三对角串行链 + 大量临时数组 + 边界/交换段 → 线程切分收益被同步吃掉。）

### prsgrd
- 入口薄壳，实现在 prsgrd3x.h 族。压力梯度是密度 Jacobian 型：沿 ξ/η 的密度差与深度差组合，每点 ~30-50 flops，i 连续。
- 与 step2d 的 2D 压力梯度共享 gzeta 中间量（VAR_RHO_2D 预积分）→ 每 3D 步只算一次 3D 压差，2D 快模用 2D 化版本（rhoA/rhoS 预积分）——**这是 ROMS 避免快模内重复 3D 压差的核心设计**，答辩可讲。

## 7. omega / wvelocity（垂向速度）

- omega：自底向上 `W(k) = W(k-1) − (Huon 差 + Hvom 差)`——**k 方向串行积分**（每列 34 次加法），全内核 ~34×4 flops/列，极轻。
- 每 3D 步调用 2 次（步首 + 校正后）→ 各 ~0.1 Mflops/调用。无优化空间，无热点。
- 答辩点：此段是"串行但轻"的典型——优化时不要被"串行依赖"吓到，先看量级。

## 8. GLS 湍流（gls_prestep 420 + gls_corstep 1123 行）

### gls_corstep 结构
1. 剪切/浮力频率：对 u/v 列差分 + den 列差分，每列 ~34×15 flops。
2. **产生/耗散段（681-800）**：每 (i,k)：
   - `Kprod = shear2·(Akv−Akv_bak) − strat2·(Akt−Akt_bak)`；
   - `Pprod` 类似 × c1/c3（稳定/不稳定分支）；
   - 耗散 `BCK = cff·(1 + dt·ψ^(-e1)·cmu·tke^e2 + …) − FCK(k) − FCK(k+1)`；
   - **`ψ^exponent` 即 pow() 调用**：每点 2-4 次 pow（ψ^(−e1)、tke^(e2)、还有 cmu_fac1 组合）——GLS 指数 N=2 时 e1/e2 为分数 → **libm pow_e7 成为 VTune 第二热点（182 s/144-720 采样，仅次于 pre_step3d 383 s）**。
3. 隐式推进：tke/gls 各一个三对角（含垂直平流项），k 串行、i 向量化。
4. 由 tke/gls 反解 Akv/Akt/Akk/Akp：每点 ~20 flops + 1 pow。

### 为什么 pow 这么贵
- `pow(x,y)` = exp(y·ln x)，双精度实现 ~50-100 条指令 + 查表分支；GLS 用 ~4-8 次 pow/点 → **等效 ~300-500 flops/点**，超过主体浮点量。
- 优化尝试：S24 队友 `-fp-speculation=fast` 等 → vali 失败/无益；Stage 129 gls_pow 路线审查 → 用 `x^a·x^b` 分解或 exp/log 改写会被 vali 判位级差异风险，且实测无显著收益 → **保留 pow，接受**。
- 答辩点：数学库函数在 HPC 内核中是"隐藏热点"，objdump 级别的 `__libm_pow_e7` 定位是队友和我们共同的 Profile 手段。

## 9. CoSiNE biology（bio_UMAINE15.h，2744 行）

### 结构（每 j：）
1. **提取**：`Bio(i,k,ibio) = MAX(t(nstp), 1e-6)`（15 数组全量拷贝 + MAX 保护）→ 17×34×1800 读。
2. 光场：每 (i,k) 1 次 EXP + 2 次 mul；PAR 逐层累积（k 串行从 N 到 1）。
3. **迭代体（BioIter=1）**：每 (i,k) 计算：
   - 温标 Q10：1 EXP；
   - 小浮游植物生长：~30 flops + 1 EXP（pnh4s1）+ 2 除法；
   - 硅藻生长：~40 flops + 1 EXP；
   - 微型/中型浮游动物摄食：~40 flops + 2 除法 + 偏好系数组合；
   - 再生/硝化/死亡/碎屑：~60 flops；
   - O₂（Qsms11 分支 k=1 特判）、TIC/Alk：~40 flops；
   - 光合速率/叶绿素更新：~30 flops；
   - 合计每点 **~250 flops + 3-5 EXP + 5-8 除法 + 若干分支（k==1 特判、min/max）**。
4. 沉降（6 个 sink 变量各一次）：
   - WENO 抛物线重构：每列 ~34×15 flops + 单调限制分支（4 个 IF）；
   - 半拉格朗日出发格搜索：**嵌套三重循环 `k → ks=k..N-1 → i`（1662-1670）——这是全程序罕见的三重循环，每列最坏 O(N²/2)≈578 次比较**；实际由于沉降距离短（dtdays·|W| 小），ks 循环提前退出，但分支成本高。
5. 回写：`t(nnew) += (Bio−Bio_bak)·Hz`（15 全量读+写）。

### 特性总结
- **分支密集**（k==1 特判、负数开关、min/max、WENO 单调限制）→ 向量化率低（实测队友 AVX2 分析：biology 主循环只有部分 ymm 化）。
- **EXP 密集**：每点 3-5 次 → `exp` 是比 pow 更快的 libm 函数（硬件无 EXP 指令，~20-40 条指令），但仍占显著比例。
- **k==1 分支**：O₂ 底层的 60 mM 半饱和特判——每次迭代两个分支路径，向量化时必须掩盖。
- 运算总量：~250 flops + ~100 指令分支/点 × 1M 点 ≈ 250-350 Mflops/调用——**计算密度最高的内核**，但被分支和 libm 拖住。
- 实测：biology 占比 4.4-5.6%（PROFILE）；VTune biology_tile 120 s（第 7 热点）。

### 优化历史
- OMP j 并行（ompbio，O33 基线已含）：~1% 级别收益。
- S45b（biology cffik exp 提出 K 循环）：**无收益 + 初版语义错误被 vali 抓超限** → 教训：数学等价改写 ≠ 性能等价，vali 是唯一裁判。
- fast=2 尝试：超限。
- 结论：**biology 是"重但难动"的内核**；编译器（PGO 布局、-ipo 内联）是已吸收的全部杠杆。

## 10. nesting.F（6597 行）— 通信与同步的重灾区

### 数据结构
- Rcontact/Ucontact/Vcontact：接触区点表（Idg/Jdg 全局坐标），粗网格 359×326 中 6 个中心 tile 供给全部接触点；细网格边界环（西列最重）。
- REFINED：双滚动时间记录（RollingTime 2 槽）→ 时空插值的数据基础。

### 调用点（每 3D 步，粗网格视角）
| isection | 时机 | 内容 | 成本 |
|---|---|---|---|
| ngetD | 粗步末 | get_contact2d×4（ζ/ubar/vbar/DU_avg2）+ get_contact3d×19（17 tracer + u + v）| **每项一次 mp_assemble（Allgather/稀疏收集）** |
| nputD | 细步首（每细步） | put_refine 时空插值 | 计算轻，边界环插值 |
| nzwgt | 每次粗步后 | z_weights 垂向插值权重 | 每接触点 ~34×10 flops |
| n2way | 粗步末 | correct_tracer + fine2coarse(2D+3D) | fine2coarse3d 面积平均 = 归约 + 回代 |

### get_contact2d 的真实工作（4465-4620）
- 每个 rank 检查点表（Npoints×4 数组 = 4×Npoints double），**只填自己 tile 内的点**（IF 归属判断）→ 未归属点留 0.0 哨兵；
- `mp_assemble(dg, model, 4·Npoints, Aspv, Ac)`：Allgather 全 64 rank 的 4·Npoints 数组 → 每 rank 从全局取非哨兵值。
- **成本构成**：一次调用 = 1 次 Allgather（消息 4·Npoints×8B；粗网格接触区 Npoints 数百→数千）。ngetD 一次步末做 ~23 次 → **单步 23 次小到中型 Allgather**（这是优化前 MPI 时间 32-40% 的主因）。
- **v22 稀疏化**：只通信"拥有数据"的 rank 子集（Allgatherv 变体）→ 消息数不变、每消息减少；**v24a 分层 Bcast**：leader 间 Bcast + 节点内共享内存 → Bcast 12.37%→1.81%。

### fine2coarse3d（面积平均回代）
- 细网格接触区内点按 Rscale²=25 个细点平均 → 粗网格点；每粗点：25 次读细网格（隔 5 跳步）+ 权重乘加。
- **访存模式**：细网格数组按 i 连续，但平均窗口是 5×5 跨步 → **stride-5 跳跃读**，cache 行利用 1/5 → 带宽浪费，但量级小（接触区窄环）。
- correct_tracer：细网格边界通量（Huon·T 累计）→ 粗网格边界列修正——同样是窄环。

### 答辩要点
- 嵌套的通信量不在"点多少"，在"**每粗步 ~23 次收集 × 每次全秩 Allgather**"的调用次数。
- 我们的两个优化（稀疏化 + 分层）分别打"消息体积"和"跨节点跳数"，都是调用次数不变前提下的体积/拓扑优化——**没有一条优化试图减少调用次数本身**（因为 ngetD 语义要求每粗步末同步），这是与"交换重构全失败"的区别。

## 11. mp_exchange / distribute（halo 与集合通信）

### mp_exchange2d/3d/4d 统一模式
1. `tile_neighbors` 查邻居 rank；
2. 打包：EW（每方向 Gsend 列 × Jlen）+ NS（Gsend 行 × Ilen），多变量按序拼入同一 send 缓冲（栈分配，大小 = Nvar·HaloSize）；
3. **先 `mpi_irecv`（W/E 两请求）→ 阻塞 `mpi_send`（W/E）**；再 NS 同构；tag 1-4 防死锁；
4. `mpi_wait` → 解包回 ghost 区。
- 消息大小：2D ≈ 720 B-2 KB；3D ≈ 34×720 B ≈ 25 KB；4D ≈ 17×25 KB ≈ 425 KB（每方向）。
- 调用频率/3D 步：2D ~10-15 次（快模段）、3D ~6-8 次（u/v/Akv/gls）、4D ~2-3 次（t、bio 输出路径）——**4D 次数少但体积大**。

### 为什么"改调用模式"全失败（v24b-v28）
- UCX 对 `Irecv→Send→Wait` 的优化：send 是 eager 协议（小消息）时发送侧不等接收侧 ready；改成 Isend+末尾 Waitall → **请求数量翻倍 + 消息生命周期拉长**，UCX 内部 RDMA 流水线被打断（v24b −50%）。
- Sendrecv（v25）：MPI 实现串行化 pair 调用 → 失去 W/E 与 N/S 的重叠（−5%）。
- 持久请求（v26）：`allocatable SAVE` 数组分配 + Start 调用开销 > 节省（−59%）。
- **教训（答辩必讲）**：小消息高频模式，通信性能由 MPI 实现的内部流水线决定；改动调用形态 = 换流水线，不是"优化"。
- 分层 Bcast（v24a）例外：它**没改单次调用形态**，只改通信拓扑（leader 先收再散）→ 成功。

### distribute 集合族
- mp_assemble（1d/2d/3d）：哨兵填充 + Allgather + 取值（已稀疏化）。
- mp_bcastf/i/l/s：分层版 `distribute_owner_reduce_scatter3d_hier.F`（v24a）→ leader Bcast + 节点内 Bcast。
- Allreduce（diag/诊断量）：占 1.2-7.6%（口径不同），HCOLL 可加速 ~30% → 整体 2.5%（v29 验证后关闭，因与 HPCX 版本兼容问题）。
